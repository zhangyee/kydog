# 同行评审（自己的稿子）

输入是**自己的稿子**（可以带上真实的审稿意见），产物是**一份修改方案**：每条意见的严重度、处置和具体改法。

评审只是手段，这个 skill 的交付物是「怎么改」。

## 和其他 skill 的分工

| | 问题 |
|---|---|
| **`/peer-review`** | **我自己的稿子该怎么改** |
| `/peer-review-response` | 别人的稿子行不行、意见怎么提 |
| `/fact-check` | 这一句话成不成立 |
| `/paper-summary` | 这篇论文怎么写进我的论文 |

某条审稿意见的**事实之争**（「审稿人说这个已被证明是错的」）先用 `/fact-check` 判——它给出的带边界判定，就是反驳或让步的依据。

## 两个入口

| 用户给了什么 | 从哪开始 |
|---|---|
| 只有稿子 | 第 1 步：模拟评审 |
| 稿子 + 真实审稿意见（decision letter、逐条 comments） | 跳过模拟，直接第 3 步分诊 |

分不清就问——这是开放题，用普通对话。

## 开工前

1. `date +%F`；`ls papers/`。
2. **read 本 skill 的 `references/review-kernel.md`**。评审内核——中性映射、整体判断、逐条 pass、严重度判据、意见五要素、编号规则——全在里面，本文不重复。**凭记忆评审必然退化**，这是硬规矩。（内核与 `/peer-review-response` 共用，两份拷贝逐字节相同，单测钉死；改内核两边一起改。）
3. 涉及文献核验时 **read fastpaper 的 SKILL.md**。
4. **会话隔离**：如果当前会话刚参与过这份稿子的写作，先提醒用户**新开会话**再跑评审——刚写过的上下文挑不出自己的毛病。新会话本身就是干净的评审环境，不需要别的仪式。

落盘纪律与 `/peer-review-response` 相同：只写最终那份报告，不建目录、不写脚本、不落中间文件。

**每进一个阶段用一两句话告诉用户你在做什么**（「先把稿子通读一遍」「在检索核验它声称的贡献」「分诊完了，开始逐条给改法」）——读稿和检索会静默几十秒，不说话用户只能盯着转圈猜。

## 第 1 步：模拟评审（只有稿子时）

按内核完整跑一遍：中性映射 → 整体判断 → 逐条检查。产物结构一样，用途不同——这不是给编辑的报告，是给自己的病历，措辞不必客气但要同样精确、同样回源。

## 第 2 步：先谈大方向

内核的整体判断（论证链、贡献定位、结构）有致命问题时，**停下来，先和用户谈方向**——这是开放题，用普通对话，不要用 ask_user_question 做成选择题。

为什么卡在这：方向错了，逐条意见就都是在错误框架里打磨；方向一调，挂在旧方向上的意见**整批作废**，让用户逐条确认它们纯属浪费。

谈出的结论（方向不动 / 收窄 / 调整主张）写进报告第一节。整体没有致命问题就不必谈，写明判断直接往下走。

## 第 3 步：分诊

给每条意见（模拟的或真实的）定两件事：**严重度**（按内核判据）和**处置**：

| 处置 | 判据 |
|---|---|
| 改 | 意见成立且改得动 |
| 挂起 | 意见成立但当下改不动，**写明卡在哪**（缺数据、要补实验） |
| 拒绝 | 意见不成立，**给可验证的理由**——检索确认过的文献、稿内原文。「我觉得差不多了」不算理由 |

真实意见另有三种情况要标出来：**审稿人之间互相冲突**（并列贴出，处置说明听谁的、为什么）；**编辑点名或 2+ 审稿人重合**（优先级最高，必须正面处理）；**审稿人误读**（稿里其实有——按「表达不清」处置去改表达，不要顶回去）。

编号：模拟意见用**全局顺序号**（Major 从 1 起、Minor 接续，严重度不编进编号——引用写「意见 N」）；真实意见**沿用 decision letter 的原编号**（R1.1、R2.3，编辑意见 E.1），报告通篇按原编号引用，和审稿人对得上号。

### 谁来拍板

- **真实审稿意见：处置必须经用户确认。** 这是作者的决定权——哪条做不到、哪条要反驳、冲突听谁的，替用户拍任何一条都是越权。用 `ask_user_question`（必须单独调用，一次至多 4 题，header 不超过 12 字符）：一题一条意见，选项是处置候选（把你的建议标 recommended，用户可自由输入）。先问 Major 和有争议的；纯事务性的 Minor（错字、引用格式）不值得问，直接建议处置。
- **模拟意见：只问依赖作者信息的。** 意见本来就是这轮评审产出的，逐条确认是走过场；真正要问的只有「处置取决于只有作者知道的事」——能不能补数据、愿不愿砍某块内容。其余的处置直接标「建议」。

## 第 4 步：逐条改法

每条意见在报告「评审意见」一节占一个块，块里写全：严重度、处置（及理由）、怎么改。**一条都不许悄悄掉**——被拒绝、被作废的也保留块，写明原因，它们是下一轮的对账基准。

处置为「改」的给三样：

- **位置**：节名 +「现文引语」
- **改成**：可直接粘进稿件的文字，或具体到能执行的操作（「删掉 4.2 节第三段，结论并入 4.3」）
- **理由**：一句

改法要诚实：补不了实验就软化主张、承认局限，**不许把「做不到」包装成「做了」**——那是把雷从评审阶段埋到发表之后。**真实返修的 R2 及以后**，改法只覆盖遗留意见，**不加审稿人没要求的新分析、新引用、新论点**——返修加戏是二轮被拒的头号原因。

## 下一轮

改完稿子再跑这个 skill，把上一份报告一并给它：**新一轮先对旧账**——上轮标「改」的逐条核对改了没有、改得对不对，然后才挑新毛病。循环由用户驱动，这个 skill 一次只跑一轮。

## 写报告

模板在 `assets/report-template.md`，用 `write` 写到**项目根目录**：

```
peer-review-<稿件简称>-YYYY-MM-DD.md
```

稿件简称用短横线连接的英文或拼音。`〔写作指导〕` 块整块不进报告；其余 `>` 引用块保留填好。**纯 Markdown，不写 HTML 标签**——KyDog 的渲染器没有 rehype-raw。

语言分两处：报告叙述用**用户的语言**；「改成」里的成品文字用**稿件的语言**（要能整段粘进稿子）。

写完在对话里给三句话：全局判断、最要紧的两三条、报告路径。

## 诚实边界

- **模拟评审挑不出毛病 ≠ 稿子没毛病。** 报告里写明这是一轮模型评审，不替代真人外审。
- **真实意见的处置一条都不许替用户决定。**
- 文献与事实断言的纪律与 `/peer-review-response` 相同：回源、不编 id、搜不到就写「在这些源、这些词下未找到」。
- **不夸大改法的效果**——「按此修改可保证接收」这种话永远不许出现。
