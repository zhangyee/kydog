# Web Research

Deliver a **Markdown research report** saved in the current project root. Inputs are HTML and plain-text web pages; do not collect PDF bodies. Operate search engines only through KyDog IAB `browser_open` and `browser_act`; `web_research_task` processes target candidates already observed in IAB. The main conversation owns searching, reflection, counterevidence, conclusions, and report writing. Background workers only fetch, parse, and extract checkable claims.

## 1. Scope the question

Preserve the original question. Internally define angles with `id`, `label`, and initial `query`, adding `rationale` when useful; state the version, time frame, and decision criteria, and submit that structure directly to the research task. **Scoping itself produces no conversation prose**: do not print “Internal research scope,” restate the original question, or display angle IDs, query tables, or unexecuted “search later” plans. Start the tool calls once the structure is ready. Show scope choices only when the research scope is ambiguous and the user must decide. A later requery does not overwrite the angle's initial `query`; each IAB search observation saves the query actually used. Do not silently change an existing angle's `label` or `rationale`; create a new angle ID. Use the default budget unless the user specifies another one, and do not silently raise it.

## 2. Search in IAB and save observations

First read the cards for all four engines under `references/`. At the start of each research run, try the **same initial query** once each in KyDog IAB on DuckDuckGo, Bing, Google, and Baidu, and save each engine's actual status. This is a per-run availability probe, not a claim that all four engines are verified. If Google or Baidu reaches a challenge page that a person can operate, follow the engine card and hand the original tab to the user with `ask_user_question` and `browserTabId`. Record `blocked` only if the user skips, the tab still has not recovered after verification, or the page offers no operable verification control; do not automatically hit that challenge again for later queries in this run. Chrome success does not establish IAB success. If the user restricts engines, try only those requested. Search later queries separately on engines that yielded extractable results in this run, recording the actual query for each engine; do not blindly repeat the same `(engineId, query)`. Check the results page and current query, then save the observation using the engine card. A form path puts the actual submit action, wait, and `extract` in one `browser_act` call and passes `research:{engineId,query,angleIds,executionPath,submitActionIndex}`. Bing's search-URL path records navigation facts in `browser_open`, then passes `executionPath:"search_url"` on the same-tab, same-query extraction. The tool saves results in the main process and returns an `observationId`, candidate count, and a small title/snippet preview. Do not hand-copy hundreds of JSON rows. Extract again after pagination or requery to get a new observation ID.

Keep and reuse a separate `tabId` for each engine. Run the initial probe as two concurrent tool batches. The first batch opens the DuckDuckGo, Google, and Baidu home pages while directly opening Bing's search URL with `research`. In the second batch, use one `browser_act` on DuckDuckGo for `type → key Enter → wait → extract`, one on Google for `type → key Escape → click → wait → extract`, and one on Baidu for `type → click → wait → extract`, while extracting the Bing tab. `browser_open` and `browser_act` can run concurrently on different tabs; the main-process queue still orders operations on the same tab. Never issue two calls for the same tab in one batch. Input actions use Electron Native dispatch and verify delivery to the target tab without changing the tab visible to the user. Only a human challenge handoff reveals the original tab through `ask_user_question` with `browserTabId`.

Follow each complete engine-card call for Google, Baidu, and DuckDuckGo; Bing uses its search URL. DuckDuckGo uses Enter as the card's primary submit action; Google and Baidu use the button click specified by their cards. After a form path fails, do not switch submit methods or construct a search URL. `submitActionIndex` must identify the actual submit `key` or `click`. The tool records submit completion, navigation confirmation, successful waits, and result extraction separately; none proves another. After a failed call, use the automatically saved failure observation. Do not blindly replay the failed action or add production DOM-diagnostic `browser_act` calls; if the engine card specifies one bounded recovery based on the new snapshot returned with the failure, follow it. A failure belongs only to the current `(engineId, query, attempt)` and must not disable the entire engine. An engine with a successful observation in this run remains eligible for later new queries. Mark the engine `blocked` and stop later queries only when a challenge still has not recovered after the human handoff above, the user skips it, or the page has no operable verification control.

Zero extracted rows do not prove zero search results. The tool automatically saves pre-submit, post-submit wait/navigation, and extract-action failures as `submission_error`, `navigation_error`, and `extraction_error`, including the failed action and original error. Do not add a duplicate `status_only` observation. Use `research.status:"explicit_empty"` only when the page explicitly reports no results, and `"blocked"` for a challenge. Record those two explicit page states with `browser_act({tabId,actions:[],research:{engineId,query,angleIds,executionPath:"status_only",status}})`; no invented action on a challenge is needed. Successful results still require `extract`. Every `research` object must include at least one non-empty `angleId`; an empty array is rejected before any page action. Snippets can guide immediate requery or counterevidence search. Until body evidence is available, do not present snippets as factual conclusions. Actual clues and evidence gaps determine whether to search again; there is no preset round count.

An observation retains the search page, engine, query, raw href, title, snippet, and angle. An external direct link extracted in IAB can be queued immediately. A search-engine-owned tracking link (such as Google `/goto`, Bing `/ck/a`, or Baidu `/link`) remains an **unconfirmed target**. First shortlist only the results that this round actually intends to fetch, using title and snippet, then pass the indexes together to `browser_open({researchResolveBatch:{selections:[{observationId,resultIndexes}]}})`. The tool reads raw links from the saved observations, navigates them through a fixed small set of IAB lanes, and saves a final address only after the main frame actually leaves the search-engine domain. `resultIndexes` are zero-based. Do not copy or rewrite opaque tracking URLs, and do not make the model resolve them one at a time. **Confirm every selected target before the observation ID's first `submit`**. An unresolved redirect must not appear in `resultIndexes`; failed indexes from the batch must not appear there either, and the agent must not submit the whole observation and resolve rows afterward. An already submitted observation ID is not automatically requeued when its URL is confirmed later. If the browser remains on the engine domain, exclude that row from this submission and retain it as a lead. Do not guess or decode tracking parameters or treat that page as article text in the ordinary fetcher. If a result item in the current IAB actually provides a separate target URL and extraction succeeds, save both the raw link and `targetUrl`; do not reuse selectors that this IAB page has not verified.

## 3. Submit a durable task and inspect incrementally

There is one research tool, `web_research_task`. On the first `action:"submit"`, pass `originalQuestion`, `angles`, and exact result choices as `observationSelections:[{observationId,resultIndexes}]`. **Do not use `observationIds` for an observation with result rows**: that compatibility field selects the entire observation and can lock ads, irrelevant items, and unresolved redirects together. Use `observationIds` only to attach a zero-row `status_only` observation so `overview` preserves that engine's actual probe status without enqueueing a source. Each `resultIndexes` list contains only external direct links or rows already confirmed through `researchResolveBatch`; **an unresolved redirect must not appear in `resultIndexes`**. For continuation, pass `researchRunId` and new selections. The first submission locks an observation so later redirect resolution cannot silently change the queued set, and another research task cannot claim it. The tool reports `acceptedIndexes`, `duplicateIndexes`, `unresolvedIndexes`, and `rejectedIndexes` per observation. In the normal flow `unresolvedIndexes` is empty. A nonempty value means the selection still contained an unresolved redirect; keep it as a diagnostic, but do not count it as enqueued or try to resolve it after the observation is locked. The tool deduplicates and **acknowledges enqueue immediately** without waiting for the whole batch. Preserve all discovery contexts when engines find the same target. Do not pass a thread ID or project path; the session binds them. The background queue outlives an agent turn, and the conversation's research task card shows its current state.

One research loop is: save this round's search observations → confirm intended tracking-link targets → `submit` new observations → use snippets immediately to identify terms, counterevidence, and the next query → call `action:"wait"` when body conclusions are needed, to await the current background batch and receive its latest state → inspect evidence and gaps from completed or failed sources → decide whether to search again, reword, seek counterevidence, or finish. `wait` awaits queued work; it does not make research judgments or require a fixed number of rounds. The task card continues to show progress while waiting. Do not repeatedly poll `inspect overview`.

Call `action:"inspect"` with `researchRunId` and `view:"overview"|"sources"|"claims"|"evidence"`. `overview` shows task state and budget plus each submitted search observation's engine, query, execution path, protocol booleans, candidate count, confirmed count, and unresolved count; the report's method section may cite only these saved facts. `sources` shows each URL's fetch/extraction state, failure reason, and discovery context; `claims` shows source-level claims and linked evidence; `evidence` checks a citation's exact excerpt, relation, and final URL in saved body text, and returns `sourceStatus`, `publishable`, and `unavailableReason`. Page `sources` and `claims` with `cursor` and `pageSize`, optionally filtering by `angleId` or source `status`; a `nextCursor` does not require reading every remaining page. `wait` already returns state and budget from the same point in time, so do not immediately repeat `inspect overview`. Read `sources` with a failed `status` only when a failure needs explanation. Read `claims` only for the current angle, evidence gap, or counterevidence, and stop paging once there is enough material to decide the next step; do not move the full claim ledger into the main conversation. Before drafting, select the citations that will actually be used, then inspect `evidence` in batches of 1–4 `evidenceIds`. Each new search must name the specific gap in an existing observation or body and what the new query will test. If no actionable query remains, report the unresolved gap.

The task-card denominator is the current count of confirmed, enqueued, deduplicated sources and can grow with supplemental searches; `300` is only the fetch-budget ceiling. `Evidence ready` means a processed source has checkable body evidence, `irrelevant` means processing completed with no relevant claim, and `failed` means fetch or extraction failed. Default capacity is 1,000 deduplicated candidates, 300 fetches, 1 GiB received bytes, and 1,800 model calls; fetch concurrency is 12 and model concurrency is 4. These are ceilings, not targets. Exhausting a global budget pauses the task and retains queued sources and search observations with deferred candidates. If continuation is needed, explicitly raise the relevant `budget` in `submit`, then call `action:"resume"`. A per-source size limit fails only that source. `pause` and `cancel` also use `web_research_task`. When an anonymous Medium fetch returns 401/403, the fetcher retries once with the persistent IAB profile's Cookie and User-Agent applicable only to `medium.com`; a second failure becomes `needs_browser`, so do not resubmit the same URL repeatedly. **No other site receives the IAB login session in a background worker.** Logging into Zhihu, X, DeepWiki, or another site in IAB does not make ordinary fetches carry that site's cookies. For 403 or `needs_browser`, seek a fetchable primary or independent source or retain an evidence gap. A 429 is source rate limiting, 521 is an origin or gateway failure, and a script shell needs browser rendering; an IAB login does not establish that any of them will recover. Preserve fetch failures, PDF media, challenge pages, irrelevant content, counterevidence, and unprocessed sources as their real states; do not relabel failures as “no relevant pages.”

## 4. Self-check and save the report

Each topical section explaining architecture, operating principles, data flow, control flow, state changes, role collaboration, or cross-component interactions must include at least one Mermaid diagram, using a standard `mermaid` fenced code block next to its explanation. Keep citations in the adjacent prose, outside Mermaid. Follow the report template for diagram types, evidence support, and inference labels.

The main conversation compares independent sources, conflicts, and time boundaries. `grounded` means the quote is locatable in saved body text, not that the claim was independently confirmed. Do not vote by search-result count. Follow the lightweight constraints in `references/report-template.en.md`, adding or removing topical sections as the question requires. Cover the question, search date, conclusions, method and coverage, findings, conflicts, limitations, and unresolved gaps. Open intended quotations through `inspect` with `view:"evidence"` first. In the **draft** passed to `complete`, cite a concrete claim as `[Source](finalURL)〔证据:evidenceId〕`. Multiple evidence items from the same source may use `[Source](finalURL)〔证据:id1,id2〕`; different sources still get separate links. The URL must exactly match the evidence source's final URL. After validation, the tool deterministically removes internal evidence IDs from the saved report, leaving clickable source links for readers.

Call `web_research_task` with `action:"complete"`, `researchRunId`, `reportMarkdown`, and optional `fileName`. If supplied, `fileName` is only a short topic slug; omit the `web-research-` prefix, date, and `.md` suffix. The tool validates every citation first. On failure it returns all structured diagnostics with line, column, excerpt, and evidence IDs in one response; it does not pause the task or write a file, so fix them together and retry. After validation succeeds, the tool stops the queue, waits for active fetches and extractions to settle, and atomically saves `web-research-<topic>-YYYY-MM-DD.md` in the project root. A unique suffix prevents overwriting an existing report. The report file card appears separately at the successful completion result; the research task card continues to show progress and status. If sources are queued, fetching, or extracting, pass `unprocessedReason` and state the same reason in the report body. A worker may fetch a GitHub Blob page through its corresponding Raw URL, while the report retains the reader-facing GitHub page URL.

After `complete` succeeds, the conversation response only says that the report was saved and summarizes at most three conclusions from the report; the file card already provides its path and open action. It **must not contain an “Execution notes” section** or repeat engines, queries, tool names, internal counts, failed calls, or debugging history. Access limitations and evidence gaps that materially affect a conclusion belong in the report's “Conflicts and unverified items” or “Limitations and open questions,” not in a second run log after the report card.
